# TREC RAG 2026: ResearchRubrics-Style Topic Rubric Generation Plan

## Purpose

Build a reproducible component that automatically generates a **topic-specific rubric file for every TREC RAG 2026 test narrative**, closely matching the schema, style, weighting system, axis taxonomy, and granularity of the organizer-shared `research-rubrics-dev-rubrics.jsonl` file.

The generated rubrics are intended to support the TREC RAG 2026 specialist judge described in `docs/trec-rag-2026-judge-implementation-plan.md`, especially:

1. rubric-conditioned pairwise/Arena judging;
2. independent pointwise rubric scoring;
3. diagnosis of answer completeness and quality beyond citation support alone;
4. optional derivation of a nugget-like content-coverage view;
5. reproducible evaluation of all public TREC RAG 2026 test topics without allowing candidate responses to define their own rubric.

The component must remain **response-independent**. It may use the public topic narrative, public track instructions, and ClimbMix corpus evidence, but it must never inspect candidate answers when generating the rubric.

Assume a **provided ClimbMix-compatible search index/service** will be available. Treat this as a required production dependency for evidence-grounded rubric generation, with a prompt-only mode retained only for ablation/fallback. The expected service can mirror the existing `trec-rag-26/tasks/search_serve` stack: natural-language search, batch search, direct document fetch, batch document fetch, and health/status endpoints.

---

# 1. Why this component should exist

TREC RAG 2026 exposes several evaluation signals:

- system-vs-system response battles;
- individualized nugget/rubric scoring;
- weighted citation precision;
- weighted citation recall.

The public development package also deliberately includes a ResearchRubrics prompt/rubric set. This strongly suggests that rubric-conditioned assessment is useful development material for the track, even though the organizers explicitly state that the development rubrics are not final official evaluation inputs.

The goal is therefore **not** to claim that our generated rubric reproduces the organizers' hidden rubric. The goal is to construct the closest principled approximation available from public information and validate it against the ResearchRubrics benchmark and public 2026 evaluator semantics.

Do **not** use TREC RAG 2025 report-level ranking as the primary optimization target for this component. The official 2025 response evaluation was based on nugget assignment, strict vital-nugget recall, sub-narrative coverage, and citation support; the public 2026 specification adds system-by-system battles and individualized nugget/rubric scoring. RAG25 therefore remains valuable for shared-component validation and transfer diagnostics, but it is not ground truth for the new 2026 rubric/Arena objective.

This plan treats rubric generation as a first-class model component rather than a prompt string embedded inside the judge.

---

# 2. Relevant published work: ResearchRubrics

The organizer-shared development rubric file comes directly from:

> Manasi Sharma et al. **ResearchRubrics: A Benchmark of Prompts and Rubrics For Evaluating Deep Research Agents.** ICLR 2026. arXiv:2511.07685.

This is the primary methodological reference for this component.

ResearchRubrics contains:

- 101 open-ended deep-research prompts;
- 2,593 expert-written rubric criteria;
- 20--43 criteria per task;
- approximately 25.67 criteria per task on average;
- prompt metadata describing domain and three task-complexity dimensions;
- six rubric axes;
- positive and negative criteria;
- criterion weights from -5 to +5;
- mandatory versus optional criteria;
- ternary per-criterion grading.

A major caveat is essential: **the original ResearchRubrics criteria were written and reviewed by humans, not generated by an LLM**. The paper explicitly reports that naive LLM augmentation/rephrasing of expert criteria substantially reduced human/LLM evaluation alignment. Therefore this implementation must not be a single call saying "write 26 rubrics for this topic." It should imitate the original multi-review process using constrained generation, evidence grounding, deterministic normalization, and independent critique.

# 4. The six evaluation axes

Use these exact axis strings in the generated compatibility file:

1. `Explicit Criteria`
2. `Implicit Criteria`
3. `Synthesis of Information`
4. `References & Citation Quality`
5. `Communication Quality`
6. `Instruction Following`

## 4.1 Explicit Criteria

Criteria directly implied by text in the narrative.

Examples of what belongs here:

- answer all named subquestions;
- compare the named alternatives;
- cover specifically requested stakeholders;
- discuss explicitly requested benefits/risks/trade-offs;
- provide the requested recommendation, explanation, timeline, or decision.

An explicit criterion should normally be traceable to a span of the narrative.

## 4.2 Implicit Criteria

Important content that a well-informed reader would expect even where the narrative does not state it literally.

Examples:

- necessary definitions;
- obvious confounders;
- uncertainty and limitations;
- relevant counterarguments;
- missing stakeholder perspectives;
- causal caveats;
- temporal context;
- distinction between correlation and causation;
- quantitative context needed to interpret a claim;
- important safety, legal, ethical, economic, or methodological implications.

This is the largest ResearchRubrics category and probably the hardest category to generate well.

## 4.3 Synthesis of Information

Criteria that require integration rather than fact listing.

Examples:

- reconcile conflicting evidence;
- compare several studies or stakeholder positions;
- explain causal relationships;
- connect evidence across requested subtopics;
- derive a balanced conclusion;
- distinguish evidence strength across claims;
- explain trade-offs rather than merely enumerate them.

## 4.4 References & Citation Quality

Criteria concerned with the use of sources.

Examples:

- important empirical claims should be backed by appropriate evidence;
- evidence should be attributed to the correct source;
- sources should be specific enough to verify the claim;
- cited evidence should actually support the associated assertion;
- the report should distinguish strong evidence from weaker commentary where relevant.

TREC RAG separately evaluates sentence/citation support. Therefore this axis should remain present for organizer-style fidelity but should not duplicate the detailed citation-support scorer.

## 4.5 Communication Quality

Criteria concerning usability and clarity.

Examples:

- appropriate organization for the information need;
- definitions where specialist terminology is unavoidable;
- readable structure;
- clear comparison of options;
- calibrated discussion of uncertainty;
- no distracting or redundant material;
- audience-appropriate explanation.

## 4.6 Instruction Following

Criteria that enforce explicit constraints independent of factual content.

Examples:

- requested scope;
- requested exclusions;
- requested audience;
- requested format;
- explicit decision or recommendation requirement;
- TREC-specific answer constraints where appropriate.

Do not use this axis as a generic bucket for factual requirements that belong under Explicit Criteria.

# 5. ResearchRubrics structural priors to reproduce

The published ResearchRubrics dataset provides useful priors for automatically generated rubrics.

Across the benchmark, criterion axes are distributed approximately as:

| Axis | Published proportion |
|---|---:|
| Implicit Criteria | 39.4% |
| Explicit Criteria | 27.7% |
| Synthesis of Information | 15.8% |
| Communication Quality | 7.8% |
| Instruction Following | 5.8% |
| References & Citation Quality | 3.5% |

These should be treated as **soft priors, not fixed quotas**.

For a 26-criterion median-like topic this corresponds roughly to:

```text
Implicit Criteria                 10
Explicit Criteria                  7
Synthesis of Information           4
Communication Quality              2
Instruction Following              1-2
References & Citation Quality      1
```

Some topics should omit an axis when it is genuinely inapplicable. The original benchmark averages about 4.74 distinct axes per task rather than forcing all six axes into every task.

TREC RAG narratives are generally richer than simple QA and usually make references/evidence relevant, so five or six active axes may be more common than in the broader ResearchRubrics benchmark. Do not force this assumption; measure it on development topics.

# 6. Criterion-count target

ResearchRubrics contains 20--43 criteria per task, with a mean of about 25.67.

Use task complexity to determine a target range rather than generating a constant number.

Recommended initial policy:

```text
low-complexity topic:       20-23 criteria
medium-complexity topic:    24-28 criteria
high-complexity topic:      29-34 criteria
hard cap:                   40 criteria
```

Because TREC RAG answers are limited to 1,024 words, avoid producing so many narrow criteria that a high-quality response could not reasonably satisfy them all.

The final criterion-count policy should be calibrated primarily against the organizer-shared ResearchRubrics development subset and the original ResearchRubrics benchmark distribution, not against RAG25 report-level rankings. RAG25 may be used only as a transfer/sanity check because its 2025 response-evaluation objective differs from the 2026 Arena/rubric objective.

# 7. Task-complexity classification

Generate the same three complexity fields as ResearchRubrics.

## 7.1 `conceptual_breadth`

Allowed values:

- `Simple`
- `Moderate`
- `High`

Operationalization from the ResearchRubrics paper:

- Simple: a single topic/domain or essentially one information framework.
- Moderate: roughly 2--5 distinct but weakly coupled subtopics/data sources.
- High: more than five sources/perspectives or clearly disjoint domains requiring cross-domain synthesis.

## 7.2 `logical_nesting`

Allowed values:

- `Shallow`
- `Intermediate`
- `Deep`

Operationalization:

- Shallow: direct retrieval or one inference operation.
- Intermediate: 2--3 dependent reasoning/subquestion stages.
- Deep: 4+ dependent stages or hierarchical analysis -> synthesis -> evaluation/planning.

## 7.3 `exploration`

Allowed values:

- `Low`
- `Medium`
- `High`

Operationalization:

- Low: goals and evaluation requirements are explicit.
- Medium: one or two important factors require prioritization/inference.
- High: substantially underspecified/open-ended and requires the system to infer several key evaluation dimensions.

Use a dedicated classification prompt and structured output. Do not infer these labels from candidate answers.

# 8. Weighting scheme

Use the exact ResearchRubrics scale.

## Positive criteria

```text
+5 / +4  mandatory / critically important
+3 / +2  important but optional
+1       slightly important / nice to have
```

## Negative criteria

```text
-5 / -4  critically detrimental / invalidating failure
-3 / -2  significant but non-fatal failure
-1       minor weakness or undesirable behavior
```

Operational rule:

- absolute weight >= 4 -> mandatory/critical;
- absolute weight <= 3 -> optional.

Do **not** ask the generation model directly to choose any integer from -5 to 5 without calibration.

Instead use a two-step process:

1. model outputs an ordinal severity/importance class;
2. deterministic code maps the class onto allowed numeric weights.

Suggested classes:

```text
CRITICAL_POSITIVE -> +5 or +4
IMPORTANT_POSITIVE -> +3 or +2
MINOR_POSITIVE -> +1
MINOR_NEGATIVE -> -1
DETRIMENTAL -> -2 or -3
CRITICAL_NEGATIVE -> -4 or -5
```

A deterministic secondary rule chooses between 4/5, 2/3, -2/-3, and -4/-5 based on whether the criterion is required for basic correctness versus strongly desirable.

This reduces arbitrary model-scale drift.

# 9. Criterion writing style

The organizer-shared examples exhibit a recognizable style. Generated criteria should deliberately reproduce it.

## Required style

- start with `The response ...` or an equally direct subject;
- describe an observable answer property;
- remain outcome-based rather than specifying how the model must reason internally;
- usually express one main requirement or one main failure mode;
- include short concrete examples when they materially reduce ambiguity;
- examples should be inside `(e.g., ...)` where possible;
- avoid vague labels such as `is comprehensive`, `is high quality`, or `is accurate` without saying what observable content demonstrates that property;
- avoid hidden chain-of-thought requirements;
- avoid criteria that can only be judged from system metadata rather than the answer;
- avoid duplicating the same requirement across axes.

# 10. Why one-shot LLM rubric generation is not acceptable

The ResearchRubrics paper contains a directly relevant warning.

Its authors tested automatic LLM augmentation of human-written rubrics. Adding concise, concrete examples improved evaluator alignment, but automatically expanding/rephrasing criteria caused a large degradation in human/LLM agreement.

The likely failure modes are:

- semantic drift;
- altered emphasis;
- verbose criteria that contain several requirements;
- invented details;
- redundant rubrics;
- examples being mistaken for exhaustive requirements;
- implicit criteria becoming over-specified;
- inconsistent weighting.

Therefore our generator must mimic the human workflow structurally:

```text
Draft -> independent review -> revision -> independent final review
```

rather than:

```text
Narrative -> one huge LLM prompt -> final rubric
```

# 15. Stage 3: build an evidence-grounded topic research pack

The biggest challenge in automatically generating high-quality **implicit** and **synthesis** rubrics is that the prompt alone often does not reveal what an expert would consider important.

Use the **provided ClimbMix-compatible index** to research every production topic before generating those axes. Prompt-only rubric generation is an ablation, not the default.

This research pack is generated from the topic and public corpus only, never participant responses.

## 15.0 Search-index client contract

Create a transport-agnostic client used by the rubric generator and, where useful, the RAG26 citation-support lane:

```python
class ClimbMixSearchClient(Protocol):
    def search(self, query: str, *, k: int = 20,
               with_text: bool = True, **backend_options) -> list[SearchHit]: ...
    def search_batch(self, queries: list[str], *, k: int = 20,
                     with_text: bool = True, **backend_options) -> list[list[SearchHit]]: ...
    def get_document(self, docid: str) -> str | None: ...
    def get_documents(self, docids: list[str]) -> dict[str, str | None]: ...
```

Normalize hits to:

```python
class SearchHit(BaseModel):
    docid: str
    rank: int
    score: float
    text: str | None = None
```

Reference the already-used `trec-rag-26/tasks/search_serve` contract where possible:

```text
POST /search
  {"query":"...", "k":20, "with_text":true,
   "complexity":64, "beam_width":2}

POST /search/batch
  {"queries":["...", "..."], "k":20, "with_text":true,
   "complexity":64, "beam_width":2}

GET /doc/{docid}
POST /doc/batch
  {"docids":["shard_...", "shard_..."]}
GET /health
```

Expected search hit shape:

```json
{"docid":"shard_00042_1337", "rank":1, "score":0.8123, "text":"..."}
```

Batch responses must preserve query order. Batch document fetches may contain partial misses; preserve them explicitly as `None` rather than silently dropping rows.

Configuration should be injected, for example:

```text
RAG26_SEARCH_BASE_URL
RAG26_SEARCH_TIMEOUT_SECONDS
RAG26_SEARCH_API_KEY   # optional, only if required by the supplied service
```

Do not hardcode the host. If the provided index is accessed locally instead of via HTTP, add a second adapter behind the same protocol rather than changing downstream code.

A search outage must not silently become "no evidence exists." Distinguish valid empty results from unavailable/malformed transport results and use bounded retries for transient failures.

## 15.1 Query decomposition

Ask a planner model for approximately 5--10 search intents covering:

- each explicit subquestion;
- likely implicit context;
- counterarguments;
- quantitative evidence;
- stakeholder impacts;
- historical/temporal context;
- evidence that could falsify simplistic conclusions.

## 15.2 Retrieval

Retrieve a broad candidate pool per intent through the provided index.

Initial recommendation:

```text
8-12 topic-derived query variants
20 documents/query
use batch search when available
union + dedupe by exact docid
rerank/select
retain 30-50 high-value documents/topic for rubric research
```

For ANN-style services similar to `trec-rag-26/tasks/search_serve`, start with:

```text
complexity=64
beam_width=2
with_text=true
```

Treat these as backend defaults, not rubric hyperparameters. If retrieval recall is poor during unrestricted development, tune retrieval parameters rather than compensating by changing rubric semantics.

Do not use candidate report citations, candidate answer claims, candidate retrieval traces, or candidate-selected documents as retrieval seeds.

Keep the exact query list and returned `docid`s in the provenance sidecar so each research pack is reproducible.

## 15.3 Evidence extraction

From the retained documents create short structured evidence notes:

```json
{
  "claim": "...",
  "docids": ["..."],
  "subtopic": "...",
  "evidence_type": "fact|number|argument|counterargument|context",
  "confidence": 0.0,
  "independent_sources": 2
}
```

These notes are for rubric generation only.

Do not insert full retrieved documents into the final rubric file.

## 15.4 Cross-source consensus

Criteria that encode specific factual content should preferably be supported by:

- one highly authoritative/relevant source; or
- two independent sources.

If the evidence is contested, generate a criterion requiring appropriate treatment of disagreement rather than asserting one side as absolute truth.

# 16. Stage 4: axis-specific candidate generation

Do not generate all axes in one call.

Run separate constrained generators to improve diversity and prevent one axis from swallowing the others.

Recommended generator functions:

```python
generate_explicit_criteria(...)
generate_implicit_criteria(...)
generate_synthesis_criteria(...)
generate_reference_criteria(...)
generate_communication_criteria(...)
generate_instruction_criteria(...)
generate_negative_criteria(...)
```

Each returns typed `RubricCandidate` objects.

Internal model:

```python
class RubricCandidate(BaseModel):
    criterion: str
    axis: Axis
    polarity: Literal["positive", "negative"]
    importance: ImportanceClass
    rationale: str
    narrative_spans: list[str]
    evidence_claim_ids: list[str]
    example: str | None
    confidence: float
```

Only `criterion`, numeric `weight`, and `axis` survive into the compatibility artifact.

# 17. Stage 5: explicit-criteria generation

Generate explicit criteria primarily from the narrative itself.

Procedure:

1. decompose the narrative into atomic asks;
2. identify named entities, perspectives, comparisons, periods, requested trade-offs, and required decisions;
3. convert each core ask into an observable outcome criterion;
4. merge only when two asks are inherently inseparable;
5. identify which asks are mandatory versus optional detail.

Mandatory explicit criteria will often receive +4 or +5.

Avoid creating an explicit criterion merely because a fact appears in retrieved evidence.

---

# 18. Stage 6: implicit-criteria generation

This stage deserves the strongest model and the strongest review because ResearchRubrics shows implicit criteria are the dominant category and one of the largest failure sources.

Inputs:

- narrative;
- explicit decomposition;
- task complexity;
- evidence notes;
- current candidate criteria to avoid duplication.

Prompt the model to answer:

> What would a knowledgeable expert expect a high-quality response to address even though the user did not literally enumerate it?

Generate candidates around:

- prerequisite context;
- important caveats;
- confounders;
- stakeholder effects;
- alternative explanations;
- limitations of evidence;
- measurement uncertainty;
- causal versus correlational distinctions;
- important costs/risks/second-order effects;
- time sensitivity;
- missing but decision-relevant quantities;
- meaningful counterarguments.

Require each generated implicit criterion to include a one-line justification explaining why it is a reasonable expectation rather than arbitrary scope expansion. The justification stays in provenance only.

---

# 19. Stage 7: synthesis criteria

Generate criteria that cannot be satisfied by copying isolated facts.

Require verbs such as:

- compare;
- reconcile;
- explain;
- weigh;
- connect;
- distinguish;
- synthesize;
- assess;
- derive;
- contextualize.

Reject pseudo-synthesis criteria that simply contain a list of facts joined by `and`.

---

# 20. Stage 8: references/citation criteria

Generate only a small number of ResearchRubrics-style citation criteria because detailed sentence/citation support is scored elsewhere in the RAG26 judge.

Typical generated items:

- important empirical/numerical claims are supported by specific sources;
- citation attribution does not misrepresent the source;
- conflicting claims are attributed rather than blended together;
- the response avoids uncited blanket assertions in evidence-sensitive portions.

Do not encode track format validation here; format validation belongs in deterministic code.

---

# 21. Stage 9: communication and instruction criteria

Generate these from the actual user need, not a universal essay template.

Bad criterion:

```text
The response contains an introduction, methods section, discussion, and conclusion.
```

unless the narrative explicitly calls for that structure.

Better criteria:

- organizes multi-stakeholder trade-offs so comparisons are easy to follow;
- defines specialized terminology needed by the intended audience;
- provides a clear bottom-line assessment where the request calls for one;
- does not bury the requested recommendation under unrelated background.

Track-level rules such as the 1,024-word cap are deterministic constraints and should not receive subjective rubric points unless experiments demonstrate that including them helps predict organizer preferences.

---

# 22. Stage 10: negative failure-mode generation

The original ResearchRubrics includes negative-weight criteria for likely pitfalls.

Generate these deliberately rather than waiting for the general axis generators to invent them.

Candidate failure classes:

- factual reversal;
- causal overclaim;
- incorrect numeric claim;
- stale/out-of-scope information;
- omission that makes a conclusion misleading;
- misleading comparison denominator;
- unqualified blanket claim;
- one-sided treatment where the request explicitly requires trade-offs;
- irrelevant tangent;
- source misattribution;
- fabricated certainty;
- contradiction with strong evidence;
- scope violation;
- format/audience violation when material.

Every negative criterion must be independently judgeable.

Avoid double-penalizing the exact negation of a positive criterion unless the error is materially more severe than simple omission.

---

# 23. Stage 11: atomicity and overlap normalization

Before weight assignment, run deterministic and model-assisted normalization.

## 23.1 Atomicity checks

An LLM critic should classify each candidate:

```text
ATOMIC
SPLIT_REQUIRED
REDUNDANT
TOO_VAGUE
UNVERIFIABLE
OUT_OF_SCOPE
```

## 23.2 Semantic deduplication

Use embeddings or a small cross-encoder to identify near-duplicates, then use an LLM only for ambiguous pairs.

Never merge criteria across axes unless they are genuinely the same outcome.

## 23.3 Contradiction checks

Detect:

- positive criterion vs negative criterion that conflict unintentionally;
- two criteria requiring mutually incompatible conclusions;
- a criterion asserting a disputed fact as universal truth.

---

# 24. Stage 12: targeted examples

ResearchRubrics reports that short concrete examples improve human/LLM alignment, while verbose synthetic expansion hurts it.

Therefore examples should be a **separate controlled pass**.

Rules:

- add examples only when they clarify the criterion;
- 1--4 short examples maximum;
- examples illustrate acceptable content but are not exhaustive;
- factual examples must come from the evidence pack or directly from the narrative;
- examples must not add a new requirement;
- do not rewrite the criterion body while adding examples;
- cap example text aggressively.

A validator should compare criterion semantics before/after example insertion and reject the example if it changes the requirement.

---

# 25. Stage 13: importance and weight assignment

Weight assignment happens only after atomicity and deduplication.

For each criterion ask an independent weighting model:

1. If omitted/violated, would the answer still be minimally adequate?
2. Does this affect factual validity, the user's core decision, or merely quality/polish?
3. For a negative criterion, does occurrence invalidate the central reasoning or merely degrade it?

Map the result deterministically to the ResearchRubrics scale.

Do not allow the same model call that wrote a criterion to assign its final weight.

---

# 26. Stage 14: independent critic/reviewer pipeline

Approximate the original multi-expert process with independent model roles.

## Reviewer A: coverage reviewer

Checks:

- all explicit asks represented;
- important implicit needs represented;
- synthesis criteria exist where needed;
- no major area of the research pack is missing.

## Reviewer B: rubric-quality reviewer

Checks:

- atomicity;
- observability;
- examples do not alter semantics;
- no criterion depends on hidden reasoning;
- axis is correct;
- weight class is plausible;
- no redundancy.

## Reviewer C: adversarial reviewer

Asks whether an answer could game the rubric while remaining poor.

Examples:

- keyword stuffing;
- listing requested concepts without synthesis;
- satisfying many optional criteria while missing a core requirement;
- citing irrelevant but authoritative-looking sources;
- verbosity that triggers more rubric matches without improving quality.

If several model families are available, use different model families for draft and review where cost permits.

---

# 27. Stage 15: final rubric-selection algorithm

At this point there may be more candidates than the target count.

Use deterministic selection subject to soft constraints.

Objective hierarchy:

1. retain every validated mandatory explicit criterion;
2. retain critical negative criteria;
3. retain high-confidence implicit criteria;
4. ensure synthesis coverage;
5. preserve applicable communication/instruction/reference axes;
6. remove lower-value redundancy;
7. approximately match ResearchRubrics axis priors;
8. remain inside topic-specific criterion-count target.

Do not select criteria solely to hit axis percentages.

---

# 28. Stage 16: output compatibility artifact

For each topic write exactly one JSONL row matching the organizer development schema.

Choose one deterministic rubric ordering policy and keep it stable because deterministic ordering improves prompt-cache reuse.

# 29. Provenance sidecar

Store generation details separately, including:

- generator version;

# 33. Prompt-cache requirements

Rubric generation will be expensive without stable caching.

Cache keys must depend only on:

- topic narrative;
- evidence pack;
- exact generation prompt;
- exact model/configuration;
- generator version.

Candidate system responses must never be part of the cache key.

Cache the search/research layer separately from rubric prompts. A research-pack cache key should include the topic hash, exact planned query list, index/service identity or version when exposed by `/health`, `k`, backend parameters, and research-pack builder version. This allows prompt experiments to reuse retrieval while still invalidating stale research packs when the index/config changes.

Ensure topic ordering, query ordering, evidence ordering, JSON serialization, and prompts are deterministic.

# 34. Structural fidelity evaluation against the organizer-shared ResearchRubrics file

Before applying the generator to RAG26 test topics, evaluate it on the public ResearchRubrics development prompts.

Procedure:

1. hide the gold rubrics from the generation process;
2. generate rubrics from the prompt using the proposed pipeline;
3. compare generated output with the organizer-shared expert rubrics.

Do **not** judge success by exact string overlap.

Measure structural statistics:

- criterion-count error;
- axes-per-topic error;
- axis distribution divergence;
- weight-distribution divergence;
- negative-criterion-rate difference;
- mandatory/optional ratio difference;
- criterion-length distribution difference;
- example-use frequency difference.

For semantic matching, build a bipartite matching between generated and expert criteria using a semantic shortlist plus an LLM equivalence check.

Report:

```text
expert criterion recall
mandatory expert criterion recall
optional expert criterion recall
negative expert criterion recall
generated criterion precision
F1
axis macro-F1
weight polarity accuracy
mandatory/optional accuracy
```

Mandatory-criterion recall should be considered the most important structural imitation metric.

---

# 35. Functional evaluation: do generated rubrics score answers like gold rubrics?

Structural similarity is not sufficient.

The real question is whether generated rubrics induce similar judgments/rankings.

For ResearchRubrics tasks with available responses:

1. score with the expert rubric;
2. score with the generated rubric;
3. compare normalized task score.

Metrics:

- Pearson correlation;
- Spearman correlation;
- Kendall correlation;
- ranking agreement among systems;
- pairwise ordering agreement;
- absolute score error.

Also compare rubric-conditioned Arena preferences using expert vs generated rubric sets.

---

# 36. Downstream TREC validation using RAG25 human truth — transfer only

After the generator has acceptable ResearchRubrics fidelity, run it on the unrestricted 2025 TREC RAG data being prepared under `docs/evaluation-2025-plan.md`, but **do not treat 2025 as the direct optimization target for the 2026 rubric/Arena design**.

The official 2025 RAG evaluation differed materially from 2026:

- 2025 response evaluation used nugget generation/assignment, `vital`/`okay` importance, strict vital-nugget recall, and sub-narrative coverage;
- 2025 separately evaluated sentence/citation support with Full/Partial/No Support and weighted precision/recall;
- the public 2026 specification introduces system-by-system battles plus individualized nugget/rubric scoring, while retaining weighted citation precision/recall.

Therefore RAG25 is valuable for **shared-component validation and transfer diagnostics**, not for choosing ResearchRubrics-style criterion wording or Arena semantics.

For every RAG25 development/evaluation topic:

1. generate a topic rubric without seeing system responses;
2. evaluate whether generated criteria semantically cover known 2025 sub-narratives/nuggets;
3. validate citation/evidence components against 2025 support truth;
4. optionally run pointwise rubric scoring and rubric-conditioned Arena/SPARROW;
5. meta-evaluate against official 2025 truth, clearly labelling report-level correlations as transfer diagnostics.

Use 2025 labels to tune only components with matching semantics, such as:

- citation support classification;
- evidence retrieval quality where judged against 2025 coverage/support;
- nugget/coverage extraction behavior;
- robustness/failure handling;
- SPARROW sparse-vs-exhaustive mechanics using the same ballot source.

Do **not** choose based on 2025 report-level correlation:

- ResearchRubrics axis proportions;
- criterion style/wording;
- criterion weights;
- rubric-conditioned Arena instructions;
- tie/both-bad policy for 2026 system battles.

Those must be selected using ResearchRubrics structural/functional validation and public 2026/RAGDoll evaluator semantics.

# 38. Freeze protocol for TREC RAG 2026 test topics

The 2026 test topics are not to become an iterative development set.

After selecting the generator using ResearchRubrics development prompts and unrestricted 2025 TREC truth:

1. freeze prompts;
2. freeze model roles;
3. freeze retrieval settings;
4. freeze weight mapping;
5. freeze criterion-count policy;
6. tag/version the generator;
7. generate rubrics for all RAG26 test topics once;
8. validate structurally;
9. do not manually edit individual test rubrics based on expected system behavior;
10. record hashes of the generated files.

Prefer zero manual content edits on 2026 topics.

# 40. Rubric scoring component

Although this plan focuses on generation, implement a compatible pointwise scorer so generator quality can be evaluated end-to-end.

Use ResearchRubrics ternary semantics:

```text
SATISFIED           1.0
PARTIALLY_SATISFIED 0.5
NOT_SATISFIED       0.0
```

For criterion `i` with possibly negative weight `w_i` and satisfaction `m_i`, compute a normalized score using the ResearchRubrics convention; verify the exact normalization against the released ResearchRubrics code rather than relying on memory.

Expose at least:

```text
RUBRIC_SCORE
RUBRIC_POSITIVE_SCORE
RUBRIC_NEGATIVE_PENALTY
RUBRIC_MANDATORY_RECALL
RUBRIC_OPTIONAL_RECALL
```

Also expose per-axis scores internally for development.

# 46. Quality gates before accepting a generated topic rubric

A topic rubric should fail validation if any of the following occurs:

- fewer than the minimum criteria;
- more than hard maximum criteria;
- no mandatory positive criterion;
- explicit asks are missing;
- all criteria come from one axis;
- unknown axis;
- weight outside -5..5;
- zero weight;
- criterion empty;
- duplicate criterion;
- critic marks a mandatory criterion as unverifiable;
- unsupported factual example;
- negative criterion polarity malformed;
- contradictions among mandatory criteria;
- task classification missing;
- evidence-dependent criteria have no provenance evidence.

Failure should trigger bounded regeneration of the failed stage rather than restarting the whole topic.

# 47. Acceptance criteria for V1

## Structural

- output is schema-compatible with organizer development rubrics;
- production generation uses the provided index unless explicitly running the prompt-only ablation;
- research packs record query/docid provenance and index configuration/version where available;
- index outages are distinguishable from valid empty search results;
- all six canonical axes supported;
- mean criteria count and axis distribution reasonably close to organizer development subset;
- mandatory/optional and positive/negative patterns validated;
- deterministic under cache replay;
- no candidate response leakage.

## ResearchRubrics imitation

On held development prompts:

- high recall of expert mandatory criteria after semantic matching;
- substantially better semantic F1 than a one-shot LLM baseline;
- strong polarity accuracy;
- acceptable axis macro-F1;
- generated rubric scoring correlates meaningfully with gold-rubric scoring.

Do not set numeric go/no-go thresholds until the development baseline has been measured.

## TREC downstream

On unrestricted 2025 truth:

- citation-support and coverage-oriented components should show useful agreement with corresponding 2025 labels;
- rubric-conditioned Arena may be compared against Arena without rubric **as a transfer diagnostic only**;
- generated rubric pointwise score may be reported against 2025 rankings but is not a selection criterion for 2026-specific rubric semantics;
- the final 2026 rubric design is selected from ResearchRubrics/public-2026 fidelity plus shared-component evidence, not from whichever variant maximizes 2025 report-level Kendall.

# 50. Important methodological boundaries

## Do not use candidate responses to create the rubric

This would make the evaluation pool-dependent and invites leakage/reward hacking.

## Do not manually optimize individual RAG26 test rubrics

The generator should be frozen before applying it to 2026 topics.

## Do not treat public ResearchRubrics rubrics as TREC RAG ground truth

They are development diagnostics from a different prompt set.

## Do not conflate ResearchRubrics scoring with official 2026 citation scoring

Citation precision/recall remains a separate specialist lane.

## Do not assume a generated criterion is correct because multiple LLM samples agree

Factual criteria should be evidence-grounded.

## Do not reward verbose rubric descriptions

The ResearchRubrics ablation suggests concise human-style criteria plus targeted examples are preferable to automatic verbose augmentation.

# 51. Final intended component

The finished system should behave like this:

```text
for each public TREC RAG topic:
    analyze narrative
    classify domain + complexity
    research ClimbMix evidence
    draft axis-specific criteria
    generate likely negative failure modes
    atomize and deduplicate
    add concise evidence-grounded examples
    independently review coverage and rubric quality
    assign ResearchRubrics-style weights
    select approximately 20-34 criteria
    validate
    emit organizer-compatible JSONL row
```

The output should look as if a careful ResearchRubrics annotator had designed a rubric for the TREC topic, while remaining fully automatic and reproducible.

The most important research question is not whether an LLM can produce superficially similar rubric text. It is whether **automatically generated, response-independent rubrics preserve enough of the expert rubric structure to improve agreement with human TREC evaluations**.
